# Playground tables live in Cosmos DB serverless behind a private endpoint

Every table of the playground (a checkers game, a blackjack table, a Drift Ledger run) and every player's career is one JSON document in an Azure Cosmos DB account: serverless, API for NoSQL, database `playground`, containers `tables`, `runs` and `players`, partitioned by game or by player. A document carries a `version` that grows by one with each change. The MCP server writes through one function, `Store.update`, which reads the document, runs a calculation on it and writes with the ETag it read as a precondition, starting over when another write came first; callers never see a conflict. The container's time to live (6 hours, 7 days, 30 days after the last write) deletes abandoned documents, so there is no reaper. The account is closed like the session store: `publicNetworkAccess` disabled, `disableLocalAuth` true, a private endpoint (`Sql`) in `snet-private-endpoints` with the zone `privatelink.documents.azure.com`, and one data role, Cosmos DB Built-in Data Contributor, for the identity of `playground-mcp`. Local runs and tests use an in-memory adapter of the same four-function interface. The Cosmos adapter runs against the emulator in `compose.yaml` before a deploy, and at every start the server runs the store's contract against the real account and reports it on `/healthz`.

The first plan was a PostgreSQL Flexible Server. The state turned out to be a document per table, written by compare-and-swap and deleted when nobody plays, and Cosmos DB has each of those as a feature: ETag preconditions, time to live, documents up to 2 MB, a query by partition for the lobby. Serverless bills nothing while nobody plays, the account provisions in minutes with no administrator step, and access is a role assignment like everywhere else in the demo. Its change feed is the way to a second replica, should one be needed (ADR 0014). The cost: a laptop cannot reach the account, so a unit test never uses the adapter that runs in Azure, and the emulator and the check at start stand in for that. The private endpoint takes the last two free addresses of `snet-private-endpoints` (one for the account, one for its region), so a third endpoint needs a wider subnet. The three lifetimes exist twice, in `infra/modules/playground.bicep` and in `src/playground/mcp/src/ports.ts`.

Rejected: PostgreSQL Flexible Server (a server that runs and bills all day, about ten minutes to provision, an Entra administrator that must be set after the server exists, tokens as passwords, and to be closed like the rest it needs a private endpoint as well, for relational features a document per table does not use; `LISTEN`/`NOTIFY` only matters with more than one replica); Azure Table Storage (a property holds 32,000 characters, so a table's state would be cut across properties; no time to live, so a reaper; no change feed; and the subscription's policy turns public access of storage accounts off, so it needs the same endpoint work for less); a container in the existing storage account, which the private endpoint already reaches (that account holds the Sessions of signed-in users, and its blob logs feed the capped workspace and an Event Grid topic, which a public game would fill with every move); Event Hubs with server push (a log, not a store: no conditional write, no read by id, retention in days; turns would still need a store, and with one replica nothing needs a bus); Cosmos DB with its public endpoint (no endpoint and no zone to deploy, but every other data store of the demo is closed, and the policy that closes storage accounts may reach it).
