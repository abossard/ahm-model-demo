# Health model agent

- One Foundry hosted agent (Agent Framework, Responses protocol 2.0.0, name `health-model-agent`) that runs Review, Explain and Design Tasks and ends each with `submit_result`. Instructions in `src/instructions.py` (a shared part and one part per Task type, added by `TaskTools`), result contract in `src/contracts/task-result.schema.json`.
- `skills/` holds the healthmodel-plan, healthmodel-analyze and healthmodel-build skills, vendored unchanged from healthmodel-skills 0.2.0 (MIT, see `skills/LICENSE`), and `healthmodel-design-rules`, which is local to this agent. `src/skillset.py` offers each Task type only its skills, with shorter descriptions: explain has analyze, review has analyze and design-rules, design has plan and design-rules. Build is not offered; its templates still feed the example words of `src/grounding.py`.
- The agent holds no Azure role. It reads Azure through the remote Azure MCP server (`MCP_URL`, read-only, the image in `src/mcp`) as the signed-in user: the eight tools in `src/azure_mcp.py`, an `Authorization: Bearer` header on every request.
- A Task type sees: explain and review `submit_result`, `load_skill` and the Azure tools; design also `run_shell` and `clone_repository`, and not `monitor_activitylog_list` (`TYPE_TOOLS` in `src/tools.py`, `visible_tools` in `src/agent.py`). `read_skill_resource` and `run_skill_script` are built by the skills provider and offered to no type. `clone_repository` (`src/clone.py`) takes the latest files of a public `https://github.com/<owner>/<repository>`, without history, into the Task folder: it downloads `https://codeload.github.com/<owner>/<repository>/tar.gz/HEAD` and unpacks it with Python's standard library (the image runs Python 3.14; `tarfile` with the `data` filter). The image has no git. The request carries no credentials or cookies, follows only redirects to codeload.github.com, stops after 120 seconds or 50 MiB, and the unpacking after 20,000 entries or 200 MiB. It unpacks plain files and folders under the archive's one top-level folder, leaves links out and refuses an archive with any other kind of entry or a path that leaves its folder. The `.cloned-from` file in the unpacked folder is how `src/grounding.py` knows a repository was read.
- Azure calls stay in the Task (`AzureScope`, `src/scope.py`): `subscription`, `resource-group`, `health-model` and any resource id must be the Task's (target subscription, the target's and the workload's resource groups, the target model). A call that names others gets an `Error: refused.` answer, not an exception. A workspace named without a resource group is looked up by the server and not checked.
- History is bounded (`InspectWindow`, `src/history.py`): `monitor_healthmodels_inspect` reads history only for an explain, for the asked entity (a `walk` is dropped), from the later of `start-at` and now minus 24 hours, or the period the instruction names (30 days at most), to `end-at` or now. `SignalHistory` and `Annotations` need an instruction that asks about the past. An explain result carries `window` (`from`, `to`) exactly when history was read.
- The user's token comes from the web app's token broker (`src/tokens.py`). Each Task envelope carries a `nonce`; the agent sends it to `POST {WEB_APP_URL}/api/agent/token`, proving itself with its own identity's token for `WEB_API_AUDIENCE` (`api://<web client id>`). The answer is held in memory per nonce until 5 minutes before it expires. Nothing is written to disk, logs, tool output, the Task folder or a result, and the model sees the nonce as `[hidden]`.
- When the broker refuses, the run goes on without Azure tools and the model submits a result that says why, with nothing proposed: the signed-in user must sign in again (`interaction_required`), an administrator must grant consent (`consent_required`), the Task ended (`unknown_task`), the web app does not accept the agent identity (`forbidden`). `rate_limited` and 5xx answers are retried with backoff first. An authorization failure of one resource is a finding, not a retry.
- Run locally from `src/agent` after `az login`, against the deployed MCP server and web app: set `FOUNDRY_PROJECT_ENDPOINT` (`https://<account>.services.ai.azure.com/api/projects/<project>`), `AZURE_AI_MODEL_DEPLOYMENT_NAME`, `AZURE_TOKEN_CREDENTIALS=AzureCliCredential`, `MCP_URL` (azd output) and `MCP_BEARER_COMMAND`, then `uv run python src/main.py`. It serves on port 8088.
- The broker cannot work locally: it accepts only the hosted agent's identity, and a local web app (`AUTH_MODE=local`) answers 404 for it. `MCP_BEARER_COMMAND` is the one override: a command whose output is a bearer token for the MCP server, run instead of the broker and held for 10 minutes, for example `az account get-access-token --scope "$MCP_SCOPE" --query accessToken -o tsv` with `MCP_SCOPE` from `azd env get-values`. The token must be for the MCP app and its `Mcp.Tools.ReadWrite` scope; the Entra setup pre-authorizes only the web app for it, so the Azure CLI needs consent first (`az login --scope "$MCP_SCOPE"`). Azure is then read with your permissions. A hosted agent (`FOUNDRY_AGENT_NAME` is set) refuses to start with it.
- Send a Task: `curl -s localhost:8088/responses -H 'Content-Type: application/json' -d '{"stream": false, "input": "Explain this entity.\n{\"task\": {\"id\": \"t-1\", \"type\": \"explain\", \"target\": {\"subscriptionId\": \"<id>\", \"resourceGroup\": \"<rg>\", \"name\": \"<model>\", \"entity\": \"<entity>\"}, \"workload\": null, \"instruction\": \"\"}}"}'`. Without the override a Task needs a `nonce` the web app issued.
- The Task folder is `tasks/<task id>` in the temp dir (`/tmp` hosted); the accepted result is `result.json` in it. Hosted, `$HOME` is a persisted volume that only root can write, and the agent runs as uid 10001, so nothing lives there.
- `submit_result` accepts a result only when it passes `contracts/task-result.schema.json` (shared with the web app), every `after` passes `contracts/model-resources.schema.json` (the property names of API 2026-11-01), and it rests on this run: a review read every entity, an explain its entity, a change of an entity starts from what the run read, a relationship joins entities that exist, `verified` and `failing` rows follow metrics or log queries the run made. It also ties a result to the workload (`src/grounding.py`): new names are lower-case kebab-case and do not reuse the words of the skill templates' examples (read from `skills/*/templates` at import) unless a resource name, the instruction or a cloned repository has them; an added resource entity points at a resource `group_resource_list` returned; an added flow or component has a resource entity below it and names its evidence in `reason`; without a cloned repository the summary says the flows are inferred from infrastructure; a new or changed signal rests on a query of this run that returned (the exact KQL with its `valueColumnName` among the columns, or the metric on that resource), and `failing` rows are only for signals the model already has. It ports the checks the web app applies after "accepted" (`src/webchecks.py`: removals, scope, size, action groups, discovered entities, signal definitions that exist, one relationship per parent and child, at most 200 changes), keeps the summary short and plain (`src/plain.py`: at most 360 characters, no ids or technical terms) and lets a replacement of an entity be a `remove` plus an `add` under another name. When Azure cannot be read, or the Task's model could not be read twice, a result proposes nothing and says why.
- A Task ends with a result (`RunPolicy` in `src/agent.py`, `submit` in `src/tools.py`, `src/reduction.py`). Every model call must call a tool, offers only the tools of its type, and the last call a type may make (12 explain, 20 review, 30 design calls, or after 75% of 240, 360 and 420 seconds, since the web app fails a Task after 10 minutes) must be `submit_result`. The first rejection lists the problems; a second identical list becomes a decision (the change ids to drop or turn into removals, and the fallbacks that are always valid); a third identical list, a fifth rejection, three calls after a rejection without a submit, or no call or second left makes the agent submit a reduced result itself: the changes that pass every check, the rest as findings that quote their problem, or an empty result with the state the run read. It is a `submit_result` call in the stream, which the web app reads like the model's own, and the tool answers `accepted` with `partial: true`. Every rejection's problems are logged at INFO with secrets redacted.
- A run can still end without a result when the model service fails or filters a call (5xx or 429 after the client's retries, content filter), when the host stops it (timeout, restart, disconnect), or when the web app gives up first.
- Per Task type the deployment and reasoning effort can differ (`task_settings` in `src/agent.py`): effort low for explain and medium for review and design, set only for `gpt-5` and `o` models, which are the ones that take it. `EXPLAIN_MODEL` and `EXPLAIN_REASONING_EFFORT` (also `REVIEW_*`, `DESIGN_*`) override them; an empty effort leaves the deployment's default. `deploy/deploy-agent.sh` sets none of them.
- Hosted facts that shaped the code: the model client repeats a streamed call's arguments, which the host server would send twice (`ArgumentsOnce`); earlier Tasks of a conversation reach the model as their messages and last results only (`EarlierTasksAsResults`); the agent opens its tools once at server start, outside any run, when it has no token, so the MCP tool connects inside a run only; every model call must call a tool (`RunPolicy`), since one run ended with an empty message after a rejection; the deployment answers 429 once its token rate is used up, which clients see as `server_error`.
- Limit, accepted: `run_shell` (design only) runs as the agent's own user (uid 10001) with python and outbound network, so a command can reach the hosts of the egress allow-list and no others: codeload.github.com, which serves downloads only and accepts no push and no form post, the Foundry account's own hosts, the web app and the MCP server. `protect_process` in `src/main.py` marks the agent not dumpable (Linux), so a command cannot read the agent's `/proc` environment or memory: the managed identity endpoint, `MCP_URL`, `WEB_APP_URL` and the tokens held in memory. The identity holds no Azure role, and the broker answers it only for the nonce of a running Task, which the shell never sees. github.com is not in the allow-list and the image has no git. Whatever a command leaves running (a background job included) is killed when its call ends.
- Tests: `uv run --project src/agent python -m unittest discover -s src/agent/tests` from the repository root. They start a fake broker, a fake MCP server and a fake Foundry on local ports and need no Azure.
- Image: `docker build --platform linux/amd64 -t health-model-agent src/agent`.
- Deploy: `deploy/deploy-agent.sh` builds the image in ACR, creates the agent version with `MCP_URL`, `WEB_APP_URL` (`https://$SERVICE_WEB_FQDN`) and `WEB_API_AUDIENCE` (`api://$ENTRA_CLIENT_ID`), then hands the agent's identity to the web app as `FOUNDRY_AGENT_PRINCIPAL_ID` (commands in `infra/README.md`). It grants the identity no Azure role. It reads the azd environment variables (the agent name is `FOUNDRY_AGENT_NAME`, `AGENT_NAME` overrides it): run it as an azd `postdeploy` hook, or export `azd env get-values` first. It retries 403 for about 3 minutes while the deployer's access propagates, and a run that timed out waiting keeps waiting for the same version.
