# The timeline is read in tiles, kept in the browser and held once

The browser reads timeline history in tiles: fixed windows that begin at multiples of their size since the epoch, a week for the states, annotations and reports of an entity, a day or a week for a series depending on its resolution level (every point, slots of 15 minutes, slots of an hour). A window that is asked for is therefore always the same request, word for word. One loader plans every read from what the viewer looks at and what is already held, batches tiles and entities into requests that fit the app's limits (400 Azure calls and 120 series a request), and is the only code that knows about tiles. The data is held once, in one store keyed by entity and by entity and signal, whatever shows it: an entity that has a row under five parents is read once. The browser keeps tiles in IndexedDB under a key that begins with a hash of the signed-in user and directory, bounded to 48 MB with the least recently used entries dropped first, and the app lets the browser's HTTP cache keep a closed window with an ETag and `Cache-Control: private, no-cache`, so every reuse is confirmed by the app after its own access check as that user (ADR 0006, ADR 0008). A selected moment reads the same tiles: the model as it was then is calculated from the store, not asked of the app.

Before this, the browser asked for the window on screen and its margins: one request for the 30 days of every entity, which passes the app's call budget for a model of about 30 entities and came back partial, and every reload read everything again. Tiles were chosen over raising the limits because the limits protect Azure and the other users of the app, and a tile fits them whatever the size of the model. The cost is that a first visit reads whole tiles, about a fifth more bytes than the window alone in the measured session, and that the thinning rule exists twice, in the app and in the browser, and has to stay the same.

Rejected: a larger call budget or a longer deadline for the overview (the request grows with the model and the limits are shared); a server route for "the model at a moment" (it needs the same histories, and the browser already holds them); keeping the browser's cache per model without the user in the key (a second user of the same browser would see the first one's data without an access check of their own); `Cache-Control: max-age` for closed windows (the browser would answer the next user from its cache without asking the app); thinning in the browser only (a month of a signal that is evaluated every minute is 43,000 points a lane to send and to hold); one array per series that mixes resolutions (the plot joins each point to the next for at most three usual intervals, so thin stretches beside dense ones would show as holes).
