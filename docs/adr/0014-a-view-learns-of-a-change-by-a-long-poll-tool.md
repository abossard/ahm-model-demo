# A View learns of a change by calling a long-poll tool

A game View keeps one call open: `wait_for_change(tableId, sinceVersion)`. The MCP server answers at once when the table is newer than that version, and otherwise holds the request until the table changes or 25 seconds pass, then answers with the whole snapshot. The View calls again with the version it now has. The answer travels as the SSE response of that POST, so it is a push on a stream that the client opened. Inside the server a commit publishes the table's id to an in-process emitter, which wakes the held requests; one replica and one writer make that complete. Each wait also applies the effects of time passing (an expired turn, a closed betting window), so a table's clock runs while someone watches it and stops when nobody does, as with the health model data in ADR 0007. The server stays stateless: no session, no standalone stream.

`tools/call` is the one request every MCP Apps host forwards for a View, so the games work in any host, not only in ours. The wire drawer shows the mechanism as it is: a request with a running timer, and its reply the moment the other player moves. It recovers on its own: every call sends the version that the View has, so a lost reply, a restart or a new revision costs one round trip and never a missed change. 25 seconds is far inside the 240 seconds after which the ingress closes an idle request. The cost is one held request per watching View, a full snapshot per change and watcher, and a wait of up to 25 seconds for a View whose request sits on the old revision while a deploy swaps them. A second replica would need a shared signal behind the same `Changes` interface: the Cosmos DB change feed (ADR 0013).

Rejected: resource subscriptions with `notifications/resources/updated` (they need a session and the standalone GET stream; a session ends with its replica and the SDK client does not start a new one; the bridge has no subscribe request and no updated notification for a View, so the host would add a hop of its own, and in any other host the board would not update); the host server pushing snapshots to the page on a channel of its own (the same private hop, by another route); polling at a fixed interval (a second of delay on every turn, or a flood of requests, and it looks like noise on the wire); a WebSocket from the View (not MCP, and the content policy of a View blocks every connection); progress notifications on one long call as the carrier of changes (the call must still end to deliver state, and the bridge relays no notification unless the host does it by hand); the change feed as the wake-up signal today (a second connection that can fail silently, to tell one process what it just did). Server notifications are shown where nothing depends on them: the Lab's countdown streams `notifications/progress` on its POST, and the host relays them to the View.
