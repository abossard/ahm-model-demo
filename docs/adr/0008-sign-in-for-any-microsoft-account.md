# Sign-in for any Microsoft account

The web app and the Azure MCP server accept users of any Microsoft Entra directory and personal Microsoft accounts, and every call still runs as the signed-in user in that user's own directory (ADR 0006). Both app registrations are multitenant (`AzureADandPersonalMicrosoftAccount`, token version 2). The MCP registration lists the web app as a known client, so one consent to the web app, requested as `<web client id>/.default`, also provisions the MCP server's service principal in the user's directory; without it the web app's token for the MCP scope could not be issued there. The web app checks each token against the issuer `https://login.microsoftonline.com/<tid>/v2.0` of its own `tid`, reads the signing keys from the common key set, refuses the personal-account tenant (`personal_account`) and, when `ENTRA_ALLOWED_TENANTS` lists directories, every other one (`tenant_not_allowed`). The on-behalf-of exchange runs at the token's directory, with one MSAL client per directory kept in a bounded cache. The workload managed identity still signs the assertion: Microsoft Learn states that an app registration that trusts a managed identity reaches resources in another tenant when it is multitenant and provisioned there, and the Azure MCP server's token validation and exchange follow the `tid` of each token when its `TenantId` is `organizations`. A personal account has no Azure in the personal-account tenant. It reaches Azure through a directory where it is a member or a guest, so the browser signs in at that directory: `organizations` for work or school accounts, and for the rest the directory the user names by domain, ID or a subscription ID, which Azure Resource Manager answers an anonymous request with. Sessions and every per-user cache and limit are keyed by tenant and user; users of the home directory keep their earlier key and blobs, so nothing is copied. A user of another directory sees the health models of the directory they signed in to, with no fallback to the deployment's own model, and Design stays with the home directory. The cost is that an administrator of each directory has to consent once, because the app has no verified publisher and users of other tenants cannot consent to Azure access for such an app, and that anyone with a Microsoft account can spend this deployment's model capacity, bounded by one running Task per user, three at once and the allow-list.

Rejected: inviting every user as a guest of this directory (an administrator's step per user, which is the AADSTS50020 a single-tenant app answers); `/common` for everyone (a personal account lands in the tenant that has no Azure); one registration per customer directory (an app and a federated credential to keep in each of them); a client secret (ADR 0006 holds); a verified publisher (it needs a Partner Center account and a work account's registration, and Bicep cannot set it); a web app route that finds the directory of a subscription (an unauthenticated route that calls out for anyone, when the browser can ask Azure Resource Manager itself and the policy names that one origin); signing keys per tenant (a multitenant app reads one key set); copying earlier Sessions to the new layout.
