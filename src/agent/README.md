# Health model agent

- One Foundry hosted agent (Agent Framework, Responses protocol 2.0.0, name `health-model-agent`) that runs Review, Explain and Design Tasks and ends each with `submit_result`. Instructions in `src/instructions.py`, result contract in `src/contracts/task-result.schema.json`.
- `skills/` holds the healthmodel-plan, healthmodel-analyze and healthmodel-build skills, vendored unchanged from healthmodel-skills 0.2.0 (MIT, see `skills/LICENSE`).
- The agent holds no Azure role. It reads Azure through the remote Azure MCP server (`MCP_URL`, read-only, the image in `src/mcp`) as the signed-in user: the seven tools in `src/azure_mcp.py`, an `Authorization: Bearer` header on every request.
- The user's token comes from the web app's token broker (`src/tokens.py`). Each Task envelope carries a `nonce`; the agent sends it to `POST {WEB_APP_URL}/api/agent/token`, proving itself with its own identity's token for `WEB_API_AUDIENCE` (`api://<web client id>`). The answer is held in memory per nonce until 5 minutes before it expires. Nothing is written to disk, logs, tool output, the Task folder or a result, and the model sees the nonce as `[hidden]`.
- When the broker refuses, the run goes on without Azure tools and the model submits a result that says why, with nothing proposed: the signed-in user must sign in again (`interaction_required`), an administrator must grant consent (`consent_required`), the Task ended (`unknown_task`), the web app does not accept the agent identity (`forbidden`). `rate_limited` and 5xx answers are retried with backoff first. An authorization failure of one resource is a finding, not a retry.
- Run locally from `src/agent` after `az login`, against the deployed MCP server and web app: set `FOUNDRY_PROJECT_ENDPOINT` (`https://<account>.services.ai.azure.com/api/projects/<project>`), `AZURE_AI_MODEL_DEPLOYMENT_NAME`, `AZURE_TOKEN_CREDENTIALS=AzureCliCredential`, `MCP_URL` (azd output) and `MCP_BEARER_COMMAND`, then `uv run python src/main.py`. It serves on port 8088.
- The broker cannot work locally: it accepts only the hosted agent's identity, and a local web app (`AUTH_MODE=local`) answers 404 for it. `MCP_BEARER_COMMAND` is the one override: a command whose output is a bearer token for the MCP server, run instead of the broker and held for 10 minutes, for example `az account get-access-token --scope "$MCP_SCOPE" --query accessToken -o tsv` with `MCP_SCOPE` from `azd env get-values`. The token must be for the MCP app and its `Mcp.Tools.ReadWrite` scope; the Entra setup pre-authorizes only the web app for it, so the Azure CLI needs consent first (`az login --scope "$MCP_SCOPE"`). Azure is then read with your permissions. A hosted agent (`FOUNDRY_AGENT_NAME` is set) refuses to start with it.
- Send a Task: `curl -s localhost:8088/responses -H 'Content-Type: application/json' -d '{"stream": false, "input": "Explain this entity.\n{\"task\": {\"id\": \"t-1\", \"type\": \"explain\", \"target\": {\"subscriptionId\": \"<id>\", \"resourceGroup\": \"<rg>\", \"name\": \"<model>\", \"entity\": \"<entity>\"}, \"workload\": null, \"instruction\": \"\"}}"}'`. Without the override a Task needs a `nonce` the web app issued.
- The Task folder is `tasks/<task id>` in the temp dir (`/tmp` hosted); the accepted result is `result.json` in it. Hosted, `$HOME` is a persisted volume that only root can write, and the agent runs as uid 10001, so nothing lives there.
- `submit_result` accepts a result only when it passes `contracts/task-result.schema.json` (shared with the web app), every `after` passes `contracts/model-resources.schema.json` (the property names of API 2026-11-01), and it rests on this run: a review read every entity, an explain its entity, a change of an entity starts from what the run read, a relationship joins entities that exist, `verified` and `failing` rows follow metrics or log queries the run made. When Azure cannot be read, a result proposes nothing.
- Hosted facts that shaped the code: the model client repeats a streamed call's arguments, which the host server would send twice (`ArgumentsOnce`); earlier Tasks of a conversation reach the model as their messages and last results only (`EarlierTasksAsResults`); the agent opens its tools once at server start, outside any run, when it has no token, so the MCP tool connects inside a run only; every model call must call a tool (`RequireToolCall`), since one run ended with an empty message after a rejection; the deployment answers 429 once its token rate is used up, which clients see as `server_error`.
- Limit, accepted: `run_shell` commands run as the agent's own user (uid 10001), so a command can read the agent processes' environment, including the managed identity endpoint and header, `MCP_URL` and `WEB_APP_URL`. The identity holds no Azure role, and the broker answers it only for the nonce of a running Task, which the shell never sees.
- Tests: `uv run --project src/agent python -m unittest discover -s src/agent/tests` from the repository root. They start a fake broker, a fake MCP server and a fake Foundry on local ports and need no Azure.
- Image: `docker build --platform linux/amd64 -t health-model-agent src/agent`.
- Deploy: `deploy/deploy-agent.sh` builds the image in ACR, creates the agent version with `MCP_URL`, `WEB_APP_URL` (`https://$SERVICE_WEB_FQDN`) and `WEB_API_AUDIENCE` (`api://$ENTRA_CLIENT_ID`), then hands the agent's identity to the web app as `FOUNDRY_AGENT_PRINCIPAL_ID` (commands in `infra/README.md`). It grants the identity no Azure role. It reads the azd environment variables (the agent name is `FOUNDRY_AGENT_NAME`, `AGENT_NAME` overrides it): run it as an azd `postdeploy` hook, or export `azd env get-values` first. It retries 403 for about 3 minutes while the deployer's access propagates, and a run that timed out waiting keeps waiting for the same version.
